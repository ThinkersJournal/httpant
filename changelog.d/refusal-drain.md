kind: A refusal now reaches the client (unread request bodies are drained)
---
- **Fix, every adapter (httpant-server; configurant's probe, httpant#70):** a handler (or a limit) that answered HTTP/1.1 without reading the request body, then had the connection closed with that body unread, lost its answer to a TCP reset on Windows: a refused `GET` with a 1 MB or 5 MB body showed the client `ConnectionAborted` and no status, 30 of 30 times (50 B and 70 KB bodies were answered; the 70 KB case reset only under full-suite load, so a smaller drain default is not the cure). The server now reads and discards the unread body before it sends the answer: up to `Limits::max_drain_bytes` (new, default 8 MiB, `0` turns it off) within `Limits::drain_timeout` (new, default 5 s); a body not finished by then makes the answer say `Connection: close`. One wrapper on the service every adapter runs (`ServeOptions::wrap`, new module `drain`), so all six adapters behave alike. Not drained: HTTP/2, a request with `Expect`, a declared length over the cap, a body something still holds (a response that streams it back), no body at all.
- **Not Breaking (PM ruling 2026-11-12):** no API is removed or changed, and `Limits` is `non_exhaustive`.

**Changes a default's behaviour, and has a cost surface:** refusals now read up to `max_drain_bytes` (8 MiB) and wait up to `drain_timeout` (5 s) before answering, where they used to be answered at once. The client chooses the body and how fast it arrives, so this is an amplification surface. What bounds it, measured: per connection, the server reads at most the cap (unit tests in `drain.rs`; `tests/drain_bounds.rs` floods 256 MiB at a 256 KiB cap and the client's writes fail long before it has offered it all) and spends at most `drain_timeout` on it (`tests/drain_bounds.rs` trickles a body one byte per 100 ms for six seconds at a 500 ms timeout and the refusal arrives at the timeout). Both tests were checked by widening the bound (cap `1 << 40`, timeout 20 s): each then fails. What does **not** bound it: HTTPAnt has no connection limit and no request-body read timeout of its own (nothing in the server crate sets one, and the adapters' own defaults apply), so the total is open connections times the per-connection bound, as it already was for any handler that reads a body: a slow client could hold such a handler for as long as it liked, where a refusal's drain now ends at 5 s. Lower the two limits (`Limits::max_drain_bytes`, `Limits::drain_timeout`) for a server that faces the open internet and has no proxy in front.
- **Known limit, actix-web:** after it has answered, actix-web reads a request body to its end whatever HTTPAnt did: with the drain on and with it off (`max_drain_bytes(0)`) it took all 256 MiB of the flood. That is the library's own behaviour below the service, so the cap cannot hold on that adapter (the timeout test holds on it). The flood test leaves actix-web out with this comment; it is the same hazard a declared-oversize `413` already had there. Not fixed here.
- Conformance case 20 `refusal-delivered` (a handler's `403` for a GET with a 1.5 MiB body and the body limit's `413` for a declared 5 MiB, sent paced and written whole before the answer is read) with the mutant `no-drain`: it fails the case with "no answer reached the client" on Windows and with a cut write on Linux (CI on both; the first version, which only read the answer last, did not fail the mutant on Linux, where the 403 stays readable after the reset). Unit tests in `drain.rs` for the cap, Expect, HTTP/2, declared length, no body and a handler that reads. Limit: a body larger than the cap is still cut off with `Connection: close`, and a client still sending may not see the answer; refusals the web library makes itself before the service runs (a malformed head) are not covered.
